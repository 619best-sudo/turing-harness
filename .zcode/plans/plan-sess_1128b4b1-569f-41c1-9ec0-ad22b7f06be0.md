## Straightforwardness classifier: skip reproduction for genuinely simple bug fixes

### Problem
The reproduction gate is armed pre-read (at `orchestrator.ts:1219`, from task text alone) and blocks *every* edit on a bug-fix run until the bug is reproduced. The only escape is `DECLARE_REPRODUCE` — the model's **unverified self-assertion** that the fix is simple. So a genuine one-line title typo in a static HTML file is blocked just as hard as a multi-file async polling bug. The user wants: after reading the files, assess whether the fix is genuinely straightforward (few files, no async/await complexity, narrow change), and if so, *lift the gate automatically* — no model self-declaration needed, no reproduction required for a trivial fix.

### Design: keep the upfront gate + add a verified lift-after-reads

Two layers, matching the user's choices:

**Layer 1 (unchanged): bug-fix detection stays upfront.** `isBugFix` is still resolved from task text at `orchestrator.ts:1219`. The gate still arms and the `BUGFIX_DIRECTIVE` still injects. This is correct — bug-fix-vs-development is a phrasing question, decidable before reads.

**Layer 2 (new): a straightforwardness assessor runs after the model has read files, and can LIFT the gate for genuinely simple fixes.** This replaces the unverified `DECLARE_REPRODUCE` self-assertion with a harness-side assessment grounded in the actual code.

### The assessor's signals (all available after reads, no new file IO)

1. **File spread** — `planTask[].files` (the planner's enumeration, when present) or the count of distinct source files the model actually read (`readPaths` filtered to source extensions). One file = strong straightforward signal; many files = not straightforward.
2. **Async/concurrency complexity** — a cheap static scan of the read file contents for `async`, `await`, `Future`, `Promise`, `.then(`, `Stream`, `Timer`, `Completer` (the exact class of code the polling bug lived in). Presence = not straightforward. This reuses the `readCache`/`readPaths` the loop already maintains — no extra reads.
3. **Change scope** — the model's declared `complexity` per plan task (`low` is a signal; `medium`/`high` is not).

The assessor combines these into a verdict: **straightforward** (≤2 source files touched/read, no async markers, declared `low`) vs **requires reproduction**. It runs once, after the planning turn (or after the first few reads on a planless run), and calls `reproductionGate.declareStraightforward(reason)` with an *evidence-backed* reason — the same mechanism the model uses today, but now verified by the harness rather than self-asserted.

### Where the assessor hooks in (the cleanest insertion point)

**On the plan path** (`!opts.skipPlan`): after the planning `runToolLoop` returns (orchestrator.ts ~1376), `planTask` is populated with `files`/`complexity` per task, and `planLoop.readPaths` carries what was read. Run the assessor here, before the work loops. If it verdicts straightforward, lift the gate.

**On the planless path** (`skipPlan`): there's no planning turn, but the work loop's first reads accumulate. The cleanest hook: run the assessor *inside the loop* after each successful `read` of a source file, once enough has been read to judge (e.g. after the first read, and re-evaluate as more come in). To avoid over-coupling, the loop exposes the read files to the gate via a small callback, and the gate holds the assessor. Cap the re-assessment at a few reads so it doesn't run forever.

### What changes concretely

**New `src/orchestrator/straightforward-assessor.ts`** (leaf module, testable in isolation):
- `assessStraightforward({ planTasks, readFiles, complexity }): { straightforward: boolean; reason: string } | undefined`
- `scanForConcurrencyRisk(content): boolean` — the static async/await/Future/Promise detector, reused from a small keyword table (no LLM).
- Returns `undefined` when there isn't enough signal to decide yet (the gate stays armed).

**`src/orchestrator/reproduction-gate.ts`:**
- Add `assessAndLift(planTasks, readFiles)` — calls the assessor; if `straightforward`, calls `declareStraightforward` with the evidence-backed reason. Idempotent (no-op once the gate is already lifted by evidence/ask/declaration).
- The existing `declareStraightforward` (model self-assertion) stays, but the assessor's verdict takes precedence when both exist (the assessor is evidence-based; the model's declaration is now a fallback, not the primary path).

**`src/orchestrator/orchestrator.ts`:**
- After the planning turn (plan path): call `reproductionGate.assessAndLift(planTask, planLoop.readPaths)`.
- Thread `assessAndLift` into the work-loop `runToolLoop` input so the planless path can re-assess after reads. The loop already has `readPaths`; it calls the assessor (via the gate) after each source read, capped.

**`src/orchestrator/loop.ts`:**
- After a successful `read` of a source file, if `reproductionGate` is present and not yet lifted, call `reproductionGate.assessAndLift(undefined, readPaths)`. Cheap (the assessor short-circuits once decided).

### What this does NOT change
- **Bug-fix detection** is untouched (still task-text, still upfront).
- **The gate still arms upfront** — a bug-fix run still gets the directive and the block until the assessor or evidence lifts it. No window where a complex fix escapes.
- **Reproduction still required for non-trivial fixes** — the assessor only lifts for genuinely narrow, synchronous, few-file fixes. The polling bug (multi-file, async, `Future`/`Timer`) would NOT be lifted.
- **The `DECLARE_REPRODUCE` escape hatch stays** as a fallback — but it's now secondary to the verified assessor, and its reason is still recorded.

### Tests (`tests/straightforward-assessor.test.mjs` + gate tests)
- **Straightforward**: one source file read, no async markers, declared `low` → lifts.
- **Not straightforward (multi-file)**: 4 files touched → does not lift.
- **Not straightforward (async)**: one file but contains `await`/`Future`/`Timer` → does not lift.
- **The polling bug case**: `.dart` files with `Future`/`Timer`/polling → does NOT lift (the regression this prevents).
- **Insufficient signal**: no files read yet → returns undefined, gate stays armed.
- **Idempotent**: calling assessAndLift after the gate is already lifted (by evidence) is a no-op.
- **Gate integration**: after a planning turn that reads one trivial file, the work-loop edit is allowed (gate lifted); after one that reads async files, the edit is blocked.

### Why this design over the alternatives
- **No new file IO** — reuses `readPaths`/`readCache` the loop already maintains and `planTask.files` the planner already produces.
- **No new LLM call** — the assessor is a cheap static heuristic (file count + keyword scan + declared complexity). A per-run LLM rater would add latency/cost to every bug-fix run for a decision that's usually obvious from the signals.
- **Replaces an unverified self-assertion with a verified one** — directly fixes the "model just declares straightforward and the gate trusts it" gap the investigation found.
- **Keeps the gate blocking for the hard cases** — the assessor is deliberately conservative: any async marker or multi-file spread means reproduction stays required.

# Plan: Adopt the flat loop in OpenWaggleMain (full migration)

## Current state (verified)

- The rebuilt turing-harness is now installed in `OpenWaggleMain/node_modules` (`loop.js`, `runToolLoop`, `RunLoopResult` all present). `pnpm install --force` done.
- `HarnessAgent` with `mode:'chain'` (the default via `OPENWAGGLE_TURING_MODE`) **already drives `run()` under the hood** (`dist/agent.js:116`). So OpenWaggle is *already running the flat loop today*.
- The adapter code, however, is written for the old 4P contract:
  - `turing-event-mapper.ts:221` switches only on `phase_start`/`phase_end`/`phase_summary` + pi events; `chain_*` hits `.otherwise(() => undefined)` and is dropped. → **no live 4P stepper**.
  - `turing-classic-run.ts:761` `buildPhaseTranscriptNode(agent.state.lastPhaseResults, …)` — `lastPhaseResults` is now `undefined` under `run()`. → **no persisted phase transcript node**.
  - `turing-run-classification.ts` walks `lastPhaseResults?.{perfect,…}`. → **failure classification degrades** (the `lastThreadSnapshot` branch still works).
- The renderer's message/tool chat UX (`chat-stream-state.ts`) treats `phase_*` as no-ops on the message list — it works under `run()` already. `phase_*` only feeds the optional `PhaseTimelineCard` stepper.

## Goal

Rebase the adapter onto the flat-loop result shape so the app **fully adopts `run()`** while keeping the UI functional. Concretely: drive the live UI and persistence from `chain_*` events + `lastRunSummary`/`lastSteps`/`lastThreadSnapshot`, not from 4P `phase_*`/`lastPhaseResults`.

## Approach

**Project the flat run into the existing transport event shape** — emit ONE synthetic "working" phase over the whole run (start on `chain_start`, end on `chain_end` carrying the run summary + steps + planSet), plus per-step `phase_end`-style detail from `lastSteps`. This keeps the renderer's `PhaseTimelineCard` and `phase_*` event types working *unchanged*, while the data now reflects a single working phase + the run's steps instead of 4 fixed phases.

### Why a synthetic phase (not a renderer rewrite)
- The renderer, the stream types, the persisted-transcript schema, IPC buffering, and the phase-tracker all key on `phase_*`. Rewriting all of that is a large, separate effort and risks the working chat UX.
- A single synthetic `'working'` phase (already a valid `AgentPhaseId` value — `phase.ts:5`) fed by `chain_*` gives a correct, live "Working… → Done" card with zero renderer changes, and the persisted transcript node carries the run summary + steps.

## File-by-file changes (all in `OpenWaggleMain/`)

### 1. `src/main/adapters/turing/turing-event-mapper.ts` (the core change)
- Add `chain_start` and `chain_end` handlers to `handleTuringEvent` (`:221`). On `chain_start`: emit one `phase_start` with `phaseId: 'working'`. On `chain_end`: emit one `phase_end` with `phaseId: 'working'`, `status` from success/aborted, and a `summary`. (No per-step live events — see note below.)
- Remove/retire the 4P-specific state: `phaseCounts`/`activePhaseLabels`/`retryPerformFromFailedVerification` and `emitPhaseEnd`/`emitPhaseSummary`'s reliance on 4P `result.*`. Keep the message/tool streaming state machine (it's pi-compatible and already works).
- `resolvePhaseSummary` and the perfect-verdict logic become dead → delete.
- The `phase_end` `pendingUserQuestion` forwarding moves to a direct read of `agent.state.pendingUserQuestion` in `turing-classic-run.ts` (it already does this at `:806`), since `run()` doesn't put it on a phase event.

### 2. `src/main/adapters/turing/turing-classic-run.ts`
- Replace `buildPhaseTranscriptNode(agent.state.lastPhaseResults, …)` (`:761`) with a new **`buildRunTranscriptNode(agent.state, …)`** that builds a `PersistedPhaseTranscript` with a single `'working'` phase: `summary` from `agent.state.lastRunSummary`, `planSet` from the run's `planSet` (read via a new agent getter — see below), tools from the streamed tool-call ids, status from `lastThreadSnapshot.disposition`. Keep the same `PERSISTED_PHASE_TRANSCRIPT_CUSTOM_TYPE` node so the persisted-card renderer is unchanged.
- `setPhaseModel('prepare'|'plan'|'perfect', …)` (`:459-462`) become no-ops under `run()`; collapse to a single `setPhaseModel('perform', …)` (the only slug the flat loop consults). Keep the others as harmless calls if simpler — they're inert.
- The result-builder's `phaseTranscriptNode` field keeps the same name/shape (no downstream change).

### 3. `src/main/adapters/turing/turing-run-classification.ts`
- Rebase `isGracefulVerificationFailure`/`isGracefulPhaseFailure`/`resolveTerminalError`/`resolveAgentEndReason` onto `lastThreadSnapshot` + `lastSteps` + `lastRunSummary` instead of `lastPhaseResults`. The snapshot already carries `disposition`/`verified`/`error`/`writtenPaths` (the `lastThreadSnapshot` branch at `:30-37` already works and stays). `phaseResultToStatus` becomes a snapshot-status mapper.
- Drop the `latestFailedPhaseResult` 4P walk.

### 4. `src/main/adapters/turing/turing-thread-snapshot.ts`
- Add a `run(task, opts)` passthrough to `createThreadSnapshotAgentHost` (alongside the existing `runChain`/`runPhase`) so follow-up-context injection is reachable if a future caller drives the host directly. Low priority since `HarnessAgent` calls `harness.run()` itself today, but completes the shim.

### 5. Agent state access for `planSet` (harness side, tiny)
- The flat loop's `planSet` lives on the `RunLoopResult`, but `HarnessAgent.state` currently exposes `lastRunSummary`/`lastSteps`/`lastThreadSnapshot` — **not** `planSet`. To build the transcript node's `planSet`, add `lastPlanSet?: PlanSet` to `HarnessAgentState` and set it from the run result in `agent.ts` (mirrors `lastRunSummary`). One small harness edit + reinstall.

## What stays unchanged (no renderer work)
- `src/shared/types/stream.ts` `phase_*` event types, `AgentPhaseId` (already includes `'working'`), `PersistedPhaseTranscript` schema.
- `PhaseTimelineCard.tsx` and all renderer chat/stream code — they continue to consume `phase_*` events; they just now render one "Working" phase instead of four.
- IPC buffering (`stream-buffer.ts`), phase-tracker, the permission callback (`request.phase` not read — phase-agnostic), the ask-user-question path.

## Multimodal (deferred — not in this pass)
The `images` arg for vision write/edit is greenfield in OpenWaggle (no caller threads attachments into `agent.prompt`). Wiring it is a self-contained follow-up; not part of this migration to keep scope bounded. I'll leave a clear TODO.

## Scope / risk
This is a focused adapter-layer migration (~4 files + tests, ~300-500 lines net), no renderer changes. Risk is concentrated in the event mapper and classification. The chat UX (message/tool streaming) already works under `run()` today and is untouched. If the synthetic-phase projection turns out to look wrong in the UI, the fallback is trivial (drop the `phase_*` emission entirely — the chat still works, you just lose the stepper card until a dedicated flat-progress UI is built).

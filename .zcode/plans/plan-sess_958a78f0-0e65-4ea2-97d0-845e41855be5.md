## Fix: close the thread-continuity read-path so follow-up prompts carry the previous run's context

### Root cause (diagnosed, not guessed)
The carry-forward mechanism is **90% wired and fully tested** — it just has one broken hop.

- **Write path works:** when a run completes, the harness builds a `ThreadRunSnapshot` (`orchestrator.ts:488`) containing the user's `task`, the generated `summary` (carrying the Perfect PASS/FAIL verdict), `writtenPaths`, `readPaths`, and `pendingUserQuestion`. OpenWaggleMain persists it as a custom node (`openwaggle.turing-thread-snapshot`) into SQLite via `persistSnapshot`.
- **Read path is broken at exactly one point:** `runTuringSession:472` calls `extractPersistedThreadSnapshot(input.persistedTranscriptNodes)` → `resolvePersistedFollowUpContext` → harness `phase-runner.ts:289-315` renders it into the next run's opening message. **But nobody populates `input.persistedTranscriptNodes`.** `runAgentKernel` (`kernel.ts:35-48`) builds the kernel input without it, so `extractPersistedThreadSnapshot` always receives `undefined` and returns `undefined` — the next run starts blind.

This is why it works *sometimes* (warm session: the in-memory `session.threadSnapshot` is reused within one process lifetime) but **not** after the things that dispose the in-memory session (app restart, session eviction, spare-session rebuild) — exactly the "doesn't understand what happened in the previous message" symptom.

The content the user wants carried — **user prompt** (snapshot.task), **files written** (snapshot.writtenPaths), **summary** (snapshot.summary) — is *already* in the snapshot. Nothing about what's captured needs to change; only the delivery.

### The fix (one location in OpenWaggleMain)

**`src/main/application/agent-run/kernel.ts` — `runAgentKernel`:** load the session's persisted nodes from the `SessionRepository` and pass them as `persistedTranscriptNodes` into `agentKernel.run(...)`.

Concretely:
1. Add `SessionRepository` to the `Effect.gen` context (same pattern `agent-run-service.ts:41` and `:79` already use).
2. Call `sessionRepo.getTree(input.sessionId)` to get the persisted `SessionNode[]`.
3. Map `SessionNode[]` → `ProjectedSessionNodeInput[]` (SessionNode is a superset; pick the fields `extractPersistedThreadSnapshot` reads: `id, parentId, piEntryType, kind, role, timestampMs, contentJson, metadataJson, pathDepth, createdOrder`).
4. Pass `persistedTranscriptNodes` into the `agentKernel.run({...})` call.
5. Make the load non-fatal: if `getTree` returns null or throws, the run proceeds without continuity (same as today) — a missing snapshot must never block a new prompt.

Everything downstream (`agentKernel.run` → `runTuringSession(input)` → `extractPersistedThreadSnapshot` → `resolvePersistedFollowUpContext` → harness `phase-runner` "THREAD CONTEXT FROM THE PREVIOUS RUN" rendering) is already built and unit-tested. No harness change is required for the basic fix.

### Edge cases handled by existing logic (verified, no new code needed)
- **Warm session short-circuit:** `resolvePersistedFollowUpContext:86` yields to the in-memory `session.threadSnapshot` when present, so the warm path is unaffected — we only fill the cold path.
- **Fresh-start runs:** a snapshot with `recommendedFollowUpMode !== 'structured_continue'` (e.g. a pending user question) is skipped at `:88`, so it won't wrongly inject a paused-run context.
- **First prompt ever:** `getTree` returns no snapshot node → `extractPersistedThreadSnapshot` returns `undefined` → no context injected. Identical to today.

### Why not also change the harness
The harness prompt rendering (`phase-runner.ts:289-315`) already emits: Previous task, route, disposition, Run summary, Files changed, Files read, Verification PASS/FAIL, Pending question, Error. That's exactly the handoff the user described. No harness edit is needed for the core fix. (If the user later wants the carried context richer — e.g. fuller diff excerpts — that's a separate enhancement to the snapshot builder, not needed to close this gap.)

### Test
Add one test in OpenWaggleMain's turing suite asserting the round-trip: given a persisted snapshot node in the repo, `runAgentKernel` passes `persistedTranscriptNodes` through to the kernel, and `extractPersistedThreadSnapshot` recovers the snapshot. The existing `turing-thread-snapshot.unit.test.ts` already covers `extractPersistedThreadSnapshot` + `resolvePersistedFollowUpContext` in isolation; this adds the missing "the app actually feeds the repo nodes in" assertion.

### Scope & risk
- **Files changed:** 1 production file (`kernel.ts`) + 1 test file. No harness changes, no DB schema changes, no port-type changes (the field already exists).
- **Risk:** low and contained — a failed load degrades gracefully to today's behavior. The change is additive (populate a field that was always meant to be populated).
- **No irreversible actions**; this is internal application logic.

# Plan: Fix MCP/Skills Loading Latency & Playwright MCP Detection

## Root Cause Analysis

### Problem 1: High latency on first prompt

The latency chain when a user sends their first message on a new thread:

```
recv message from renderer
  → preflight (fast: JSON config reads)
    → runTuringSession
      → checkoutWarmProjectSession
        ├─ spare ready? → instant ✅
        └─ spare NOT ready? → prewarmProjectMemory (BLOCKS)
             → createWarmProjectSession
                ├─ harness.createProjectSession()  (~500ms, memories)
                └─ attachOpenWaggleRuntime()       (5-30s cold, MCP spawns)
      → attachOpenWaggleRuntime()                   (called AGAIN, hits fast-path if prewarm)
      → agent.prompt() ← LLM finally starts here
```

**Root cause**: `createWarmProjectSession` calls `attachOpenWaggleRuntime()` inside the prewarm, connecting ALL MCP servers eagerly. This makes prewarm take 5-30 seconds. If the prewarm hasn't completed when the user sends their first message, they hit a full cold build that blocks before the LLM sees the prompt.

Additionally, `runTuringSession` always awaits `attachOpenWaggleRuntime()` before calling `agent.prompt()`, so even when the prewarm did complete, MCP connection is on the critical path.

**The prewarm should be FAST (just harness + memories). MCP connection should be DEFERRED.**

### Problem 2: Playwright MCP not used — model installs Playwright manually

**Root cause**: When MCP servers fail to connect, the model only sees vague "OPENWAGGLE MCP BRIDGE NOTES" in the prompt. It doesn't get:
1. A clear list of which MCP tools ARE available (with their exact tool names)
2. A clear list of which MCP servers FAILED (so it knows NOT to expect those tools)
3. An instruction to NOT work around missing MCPs with manual package installation

The model falls back to `bash: npm install playwright` + manual scripting because it doesn't understand the MCP tool landscape.

## Changes

### turing-harness (library) — 2 files

#### 1. `src/orchestrator/loop.ts` — Dynamic tool resolution

**Why**: Currently `runToolLoop` captures `input.tools` ONCE at loop start via `const toolByName = new Map(...)`. Tools added to the registry after the loop starts are invisible to the model. We need the loop to pick up newly-connected MCP tools each turn.

**Changes**:
- Add optional `resolveTools?: () => AgentTool[]` to `ToolLoopInput` 
- At the start of each turn (before `streamToMessage`), if `resolveTools` is provided, call it to get fresh tools and update `context.tools` and `toolByName`
- Add a `toolResolutionLag` log entry when new tools are discovered mid-loop

#### 2. `src/orchestrator/orchestrator.ts` — Pass dynamic resolver to loop

**Why**: The flat loop `run()` calls `this.resolveLoopTools()` once and passes the static array to every sub-loop. It needs to pass a dynamic resolver instead.

**Changes**:
- In `run()`, instead of `const tools = this.resolveLoopTools()`, pass `resolveTools: () => this.resolveLoopTools()` into each `runToolLoop()` call
- This lets the loop discover newly-added MCP tools mid-run

### OpenWaggleMain (app) — 3 files

#### 3. `src/main/adapters/turing/turing-memory-prewarm.ts` — Remove MCP connection from prewarm

**Why**: `createWarmProjectSession` currently calls `attachOpenWaggleRuntime()` which makes prewarm take 5-30 seconds. MCP connection should happen during run setup, not prewarm.

**Changes**:
- Remove the `attachOpenWaggleRuntime` call from `createWarmProjectSession` (lines 120-157)
- Remove the `bridgeAttached` and `bridgeSignature` fields from `WarmProjectSession` (they're no longer relevant)
- Add a `runtime` field to `WarmProjectSession` that stores `{ mcpSettings, standardsContext }` for deferred bridge attach
- The prewarm now takes ~500ms (harness + memories only), making it almost certain to complete before the user sends their first message

#### 4. `src/main/adapters/turing/turing-openwaggle-bridge.ts` — Background MCP + better tool visibility

**Why**: Two fixes in one file:
- **A) Background MCP connection**: Add `connectMcpBackground()` that returns immediately but connects MCPs asynchronously. Each connected MCP's tools flow into the registry dynamically.
- **B) Better tool visibility in prompt**: Add an explicit "AVAILABLE MCP TOOLS" section listing every connected MCP tool by name, and an "UNAVAILABLE MCP SERVERS" section listing failed servers. Add anti-workaround instruction.

**Changes**:

A) New function `connectMcpBackground(session, runtime, pool?): { ready: Promise<BridgeResult> }`:
- Registers no tools initially
- Spawns MCP connections in the background (reusing `attachOpenWaggleRuntime`'s connection logic but without blocking)
- Each server that connects adds its tools to the session registry immediately
- Returns a `ready` promise that resolves when all connections settle
- Logs each connection as it completes

B) Enhanced `buildOpenWaggleRuntimePrompt`:
- Add "CONNECTED MCP TOOLS" section listing every MCP server and its tool names
- Add "UNAVAILABLE MCP SERVERS" section explicitly naming failed servers
- Add instruction: "Do NOT install packages (npm install, pip, etc.) to work around unavailable tools. Use only the tools listed above."

#### 5. `src/main/adapters/turing/turing-classic-run.ts` — Non-blocking MCP + tool visibility

**Why**: Currently `runTuringSession` awaits `attachOpenWaggleRuntime()` before calling `agent.prompt()`. With dynamic tool resolution in the loop, we can start the agent immediately and let MCP tools appear mid-run.

**Changes**:
- Call `connectMcpBackground()` instead of `await attachOpenWaggleRuntime()`
- Start `agent.prompt()` immediately — the model begins with built-in tools
- MCP tools appear in the registry dynamically as they connect
- The bridge result (issues, connected MCPs) is still captured for the debug event and snapshot
- The runtime prompt now includes the "CONNECTED MCP TOOLS" section (initially empty, but the model knows more tools may arrive)

## Impact

### Latency improvement (Problem 1)
| Scenario | Before | After |
|---|---|---|
| Prewarm completes before first message | ~500ms (fast-path hit) | Same |
| Prewarm NOT ready, cold path | 5-30s (MCP spawn + memories) | ~500ms (memories only) |
| First prompt → LLM starts thinking | 5-30s | ~500ms |

The prewarm is now fast enough to almost always complete before the user types their first message. When it doesn't, the cold path is still fast because MCPs are deferred.

### MCP detection (Problem 2)
| Scenario | Before | After |
|---|---|---|
| Playwright MCP connected | Model sees tools but doesn't know they're MCP-provided | Model sees explicit tool list: `browser_navigate, browser_snapshot, ...` |
| Playwright MCP FAILED | Model sees vague "MCP bridge note", falls back to `npm install playwright` | Model sees "UNAVAILABLE: Playwright MCP failed to connect" + "Do NOT install packages manually" |
| Dynamic tool arrival | N/A (tools never appear mid-run) | Model discovers new tools each turn; can use Playwright tools that connect 2 seconds into the run |

### Risk assessment
- **Dynamic tool resolution**: Low risk. The loop already validates tool names against the map; re-resolving just refreshes that map. If a tool disappears between turns (MCP crash), the next call gets "Unknown tool" — same as today.
- **Background MCP connection**: Low risk. MCP connection is already parallelized in `attachOpenWaggleRuntime`. `connectMcpBackground` uses the same logic, just without blocking the return.
- **Removing prewarm bridge**: Low risk. The bridge was redundant — `runTuringSession` always calls it again. The fast-path cache just won't be pre-populated, but the run setup will populate it.
